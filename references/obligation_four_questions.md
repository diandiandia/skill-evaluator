# 规则与复杂度的四问

用来诊断可疑规则、门禁、字段、阶段或角色；不是逐句填表的强制仪式。
过多无关指令可能增加理解成本，但不能把“条款越多遵守率必然越低”当作已证定律。

## 1. 何时生效，守护什么？

写清触发条件、保护的不变量或用户约束。
有些核心约束始终生效，不必人为加 IF；只在少数场景有用的指引可按需加载。
不要因规则常驻就自动删除。

## 2. 谁消费，改变什么行为？

沿 Agent、脚本、宿主或人工执行者追踪其输出/判断。
若 True/False 都进入相同动作，先检查它是否有记录、告警或审计用途，再判为死门禁。
没有脚本消费者不等于没有消费者。

## 3. 删除会失去什么保证？

寻找历史失效、最小反例、领域标准、风险模型或用户明确要求。
没有历史事故不代表防护没有价值；相反，“以后可能有用”也不能单独证明复杂机制合理。
删除可能改变风险边界时应先做对照/回归，而不是武断精简。

## 4. 为什么必须由 Skill 显式提供？

是特定领域知识、宿主行为、易错约束还是普通知识？
“模型应该懂”只是待检验假设；结合实际版本/样例观察。输出格式与数据完整性等
即便概念简单，也可能因契约需要而必须显式规定。

## 裁决与常见缺陷

| 现象 | 要查的证据 | 可选处理 |
|---|---|---|
| 环境/项目耦合 | 是授权配置/示例还是意外依赖？迁移是否真的失败？ | 参数化、相对路径、明确部署边界；不因名称本身判死刑 |
| 设计偏见 | 偏好来自用户要求、领域约束还是作者习惯？是否限制合法任务？ | 改为按条件建议；硬约束保留依据 |
| 死规则/幽灵门禁 | 有没有真实消费者、日志用途或失败分支？ | 删除、接线或合并，并验证下游 |
| 过设计 | 额外状态/角色/字段带来什么保证和成本？简单方案能否达到同一约束？ | 最小替代、消融实验；无测量不宣称必然提效 |

最终可选：**保留 / 条件化 / 移至参考 / 合并 / 删除 / 待实验**。
每个建议附“改变什么、保留什么、怎么验证”，不为精简而牺牲正确性。
